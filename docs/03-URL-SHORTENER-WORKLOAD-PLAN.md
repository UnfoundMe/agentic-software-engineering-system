# Plan 2 of 2 — URL Shortener, Implemented *by* the Orchestrator

**System:** `url-shortener` (ASP.NET Core 9 / C# / PostgreSQL / Redis)
**Status:** Proposed
**Date:** 2026-09-12
**Companion:** `02-ORCHESTRATOR-IMPLEMENTATION-PLAN.md`

---

## 1. Framing — what this document is, and is not

Per the locked decision, the URL Shortener is **fully agent-generated from the requirement alone**. This document therefore does **not** contain an implementation plan in the usual sense. There is no task list of classes to write, because writing them is the orchestrator's job and demonstrating that is the point of the exercise.

What this document defines is the **experimental apparatus**: the inputs the orchestrator is given, the contract it must satisfy, the independent oracle that grades it, and the choreography of each run.

| Authored by hand (by me) | Generated by agents |
|---|---|
| The four requirement texts (§2, §3.1, §6.1, §7.1, §8.1) | Solution and project structure |
| `CONTRACT.md` — the fixed HTTP contract, stated *inside* the requirement | Every line of C# |
| `conformance/` — black-box acceptance oracle | All unit and integration tests |
| `GROUND_TRUTH.md` — expected impact sets, written against the frozen baseline *(Stage 2)* | EF Core entities and migrations |
| Policy rule packs | API documentation and README |

**The conformance oracle is never placed in any agent's context.** It exists precisely because the implementation *and its tests* are both agent-generated; without an external oracle, deterministic validation would be self-graded and architectural rule C-14 ("deterministic validation authoritative") would be hollow.

## 2. One codebase, four scenario classes

The workload is a single codebase that evolves across four orchestrator runs. This is deliberate: four disconnected fixtures would demonstrate four demos, whereas one evolving codebase demonstrates a **lifecycle**, and each run's output becomes the next run's brownfield input.

| Stage | Run | Class | Graph | Requirement quality |
|---|---|---|---|---|
| **1** | 1 | `greenfield` | Full, minus codebase index/impact | Well-defined |
| **1** | 2 | `greenfield_ambiguous` | Full + bounded clarification cycle | Deliberately vague |
| 2 *(deferred)* | 3 | `brownfield` | Full, with Roslyn index + impact | Well-defined |
| 2 *(deferred)* | 4 | `test_docs` | Reduced — no design stage, no Gate 2 | Well-defined, narrow |

**Stage 1 is greenfield only.** It still covers both declared requirement-quality classes — well-defined and ambiguous — so no part of the scope statement goes unexercised. Runs 3 and 4 wait until the greenfield path is solid.

After Run 1 the output is **frozen and committed** to `workloads/url-shortener/baseline/`, which becomes the brownfield input when Stage 2 begins.

**Cost of the deferral, stated plainly:** Run 4's reduced graph was the cleanest single demonstration that graph shape is a function of requirement class. Stage 1 still shows two distinct shapes — Run 2's clarification cycle is a genuine backward edge that Run 1 does not have — but the evidence is weaker until Stage 2 lands.

## 3. Run 1 — Greenfield (well-defined)

### 3.1 Requirement text given to the orchestrator

> Build a URL shortening service as an ASP.NET Core 9 Web API targeting .NET 9, backed by PostgreSQL via Entity Framework Core.
>
> It must expose:
> - `POST /api/v1/urls` accepting `{"url": "<absolute http/https url>"}`, returning `201 Created` with `{"code": "<base62>", "shortUrl": "<absolute url>"}`
> - `GET /{code}` returning `302 Found` with a `Location` header pointing at the original URL, or `404 Not Found` if the code is unknown
> - `GET /health` returning `200 OK`
>
> Short codes must be Base62, collision-free, and at most 10 characters. URL mappings must be durably persisted. Invalid input must return `400` using RFC 7807 Problem Details. Provide unit and integration tests.

The contract is stated *in the requirement* rather than assumed, which keeps generation objective without pre-writing any implementation.

### 3.2 Ambiguities the Requirements Agent is expected to surface at Gate 1

Even a "well-defined" requirement leaves genuine judgment calls, and surfacing them is the measured behaviour:

1. Submitting the same long URL twice — new code each time, or return the existing one?
2. `302` is specified, but is that correct given that `301` is cacheable and would break future analytics?
3. Are custom or vanity aliases in or out of scope?
4. Is there any authentication on the create endpoint, or is it open?
5. What is the maximum accepted URL length?
6. Are codes generated sequentially (enumerable, therefore scrapeable) or randomly?

A human resolves these at Gate 1, and each resolution is recorded in the `AmbiguityRegister` artifact with its rationale, becoming part of the decision lineage.

### 3.3 Node choreography

| Node | Produces | Gate |
|---|---|---|
| `INTAKE` | `RequirementInput` | — |
| `REQ_ANALYSIS` | `RequirementSpec` + `AmbiguityRegister` | **Gate 1: human sign-off** |
| `ARCH_DESIGN` | `DesignSpec` + `ADR-001` (project layout, persistence, code-generation strategy) | **Gate 2: design approval** |
| `SCAFFOLD` | `.sln`, `.csproj` files, pinned `Directory.Packages.props`, frozen interface/DTO signatures | Exit: `dotnet restore` + `dotnet build` on the empty skeleton |
| `DECOMPOSE` | `TaskGraph` → dynamic subgraph | Admission check: schema, acyclicity, policy |
| `IMPL_TASK_*` | `CodePatch` per task, in parallel where independent | Exit: `dotnet build` **per task** |
| *barrier* | — | `ALL` |
| `TEST_GEN` → `TEST_RUN` | `TestSuite`, results | Bounded `REPAIR` cycle, k ≤ 2 |
| `CODE_REVIEW` ∥ `SEC_SCAN` ∥ `DOCS_GEN` | `ReviewReport`, violations, docs | Join at `QUALITY_GATE` |
| `QUALITY_GATE` | — | **Conformance oracle runs here** |
| `RELEASE_READINESS` | `ReleaseReport` | **Gate 3: release approval** |
| `FINAL_SUMMARY` | `RunSummary`, generated from the event log | — |

Expected parallelism: a plausible decomposition yields independent tasks for the domain entity, the Base62 encoder, the persistence layer, and the API surface — the encoder and the entity have no dependency on each other, satisfying the "≥2 tasks in parallel" success criterion.

`SCAFFOLD` exists because parallelism is what creates integration risk: without frozen interfaces, two tasks can each compile alone and fail together at the barrier. Freezing the contract before fan-out removes that class of failure. See `02` §7.1.

### 3.4 Reference architecture — **grading oracle only**

Recorded here so the output can be assessed against a considered target. **It is never placed in an agent's context**; if an agent converges on something materially different but passes the contract and the oracle, that is a legitimate outcome and the divergence is recorded rather than penalised.

```
UrlShortener.sln
  src/UrlShortener.Api/             endpoints, DI wiring, Problem Details
  src/UrlShortener.Core/            ShortUrl entity, Base62 encoder, abstractions
  src/UrlShortener.Infrastructure/  EF Core DbContext, repository, migrations
  tests/UrlShortener.Tests/         unit + integration
```

`ShortUrl`: `Id (bigint identity)`, `Code (text, unique)`, `LongUrl (text)`, `CreatedAt (timestamptz)` — with `ClickCount` arriving in Run 2 and `ExpiresAt` in Run 3.

## 4. Validation pipeline (.NET)

| Layer | Check | Failure route |
|---|---|---|
| L1 Schema | `CodePatch` / `TestSuite` pydantic validation | one repair prompt, then fail node |
| L2 Static | `dotnet build -warnaserror`, `dotnet format --verify-no-changes`, `dotnet list package --vulnerable`, secret scan | `REPAIR` |
| L3 Dynamic | `dotnet test` with coverage; coverage delta ≥ 0 | `REPAIR`, bounded |
| L3+ | **Conformance oracle** (§5) | `REPAIR`, then escalate |
| L4 Semantic | Critic agent, rubric, mandatory `file:line` citations | escalate to human |
| L5 Human | Gates 1–3 | reject → re-plan |

All layers execute inside the sandbox worktree against the throwaway `workload_test` database. Nothing is promoted to `workloads/url-shortener/generated/` until Gate 3.

## 5. Conformance oracle (hand-authored, agent-invisible)

A black-box HTTP suite that boots the built service on an ephemeral port and asserts only the contract from §3.1:

1. `POST /api/v1/urls` with a valid URL → `201`; body contains `code`; `code` matches `^[0-9A-Za-z]{1,10}$`
2. `GET /{code}` → `302` with `Location` exactly equal to the submitted URL
3. `GET /{unknown}` → `404`
4. `POST` with a malformed or non-http(s) URL → `400` with an RFC 7807 body
5. `GET /health` → `200`
6. Two distinct URLs never collide on a code
7. Mappings survive a process restart (durability)

Run 2 extends it with click-count accuracy and denylist rejection; Run 3 adds cache-hit equivalence, expiry behaviour, and rate-limit responses.

## 6. Run 3 — Brownfield enhancement — **DEFERRED TO STAGE 2**

> Retained in full so the Stage 2 design is settled. Nothing here is built yet.

### 6.1 Requirement text

> Add Redis caching for redirect lookups, falling back to PostgreSQL on a cache miss and populating the cache on read. Support optional URL expiration, where an expired code returns `410 Gone`. Enforce per-API-key rate limiting on the create endpoint, returning `429` with a `Retry-After` header when exceeded. Existing clients must continue to work unchanged.

### 6.2 Expected impact set (the substance of `GROUND_TRUTH.md`)

Hand-authored against the frozen baseline **after** Run 1, and used to score the Roslyn analyzer by precision and recall:

| Dimension | Expected |
|---|---|
| Modified symbols | redirect endpoint handler, URL repository, `ShortUrl` entity, `DbContext` configuration, `Program.cs` DI registration |
| New symbols | cache abstraction + Redis implementation, rate-limit middleware, expiry policy |
| Data flow | new `ExpiresAt` column → migration → repository read path → redirect response |
| API surface | `410` and `429` added to the redirect and create contracts; no existing route or status code removed |
| Policy interception | the migration touches `**/Migrations/**`, which **must** trigger the change-control rule and require human approval |

That last row is intentional. The brownfield run is designed so a policy guardrail fires on a genuine engineering action rather than a contrived one.

### 6.3 Backward-compatibility gate

An exit-gate assertion re-runs the **Run 1 conformance oracle unchanged**. Any regression in the original contract fails the gate. This is the workload-level expression of "no breaking public-API change without an ADR and a version bump."

## 7. Run 2 — Ambiguous greenfield requirement *(Stage 1)*

### 7.1 Requirement text

> Our marketing team needs a way to share campaign links that are short and tidy, and we want to know how those links are performing. Build it.

Recast as greenfield rather than an enhancement, so it runs in Stage 1 without any brownfield capability. It is the same codebase's *second* independent build, not a modification of the first — the orchestrator is given no prior artifacts.

### 7.2 What is being measured

Not the code — the **ambiguity handling**. The Requirements Agent should decline to proceed to design and instead produce an `AmbiguityRegister` covering at least:

- "Short and tidy" — is this a URL shortener at all, or custom vanity domains, or both?
- Who are the users? Is there authentication, and are links scoped to a team?
- "Performing" — click counts? unique visitors? referrer? geography? conversions?
- Real-time or batch aggregation? What retention period?
- Does capturing IP or user-agent create a GDPR obligation, and who owns that decision?
- Is the deliverable an API, a dashboard, or an export?
- What happens to a link after a campaign ends — expiry, or permanent?

Gate 1 is expected to be **rejected at least once**, exercising the bounded clarification cycle (`REQ_ANALYSIS → GATE_1 → rejected → REQ_ANALYSIS`, max 3). The rejection, the human's clarification, and the revised spec all enter the decision lineage — this is the run that demonstrates decision provenance most clearly, because the final design is traceable to a human sentence rather than to the original requirement.

Scope after clarification is expected to narrow to the Run 1 contract plus click counting with asynchronous aggregation, and a local denylist behind a pluggable `ISafetyProvider` (remote implementation stubbed, preserving offline determinism).

## 8. Run 4 — Test and documentation improvement (reduced graph) — **DEFERRED TO STAGE 2**

### 8.1 Requirement text

> Raise integration test coverage of the redirect and expiration paths to at least 80%, and generate OpenAPI documentation plus a README quickstart.

### 8.2 Why this run matters disproportionately

It is the cheapest run to build and the strongest single piece of evidence for the "non-linear" claim, because it proves **the graph shape is a function of the requirement class**, not a fixed pipeline:

```
INTAKE → REQ_ANALYSIS → GATE_1 → CODEBASE_INDEX → IMPACT_ANALYSIS → DECOMPOSE
       → [ TEST_GEN ∥ DOCS_GEN ] → TEST_RUN → QUALITY_GATE → FINAL_SUMMARY
```

No `ARCH_DESIGN`. No Gate 2. No Gate 3. Migration policy disabled, because no schema change is in scope. A fixed-pipeline orchestrator cannot do this; a graph-driven one does it by selecting a different workflow definition.

## 9. Workload-specific risks

| Risk | Mitigation |
|---|---|
| Agent-generated code does not compile | `SCAFFOLD` freezes interfaces before parallel fan-out; `dotnet build` is a per-task exit gate; compiler diagnostics feed a bounded `REPAIR` ladder. Reframed in `02` §7.1 — the realistic cost is extra repair iterations, not a blocked demo |
| Agent-generated EF migrations run against a real database | Generate-and-classify, never blindly apply; raw SQL banned; human reviews the SQL not the C#; transactional DDL with lock and statement timeouts; disposable schema. Full pipeline in `04-DATA-AND-MIGRATION-STRATEGY.md` §4 |
| Generated app calls `Database.Migrate()` at startup | Banned by the `no_runtime_migration` policy rule and checked by the static validator — `04` §4.7 |
| Agent-written tests are weak and pass trivially | The independent conformance oracle is the authoritative acceptance signal; coverage delta is a secondary check |
| Redis introduces a second failure mode into the redirect path | Run 3's requirement mandates cache-miss fallback; the oracle asserts identical behaviour with Redis stopped *(Stage 2)* |
| Base62 collisions under concurrency | Oracle test 6 plus a database unique constraint on `Code`; a collision must surface as a failure, never as silent overwrite |
| Run 2's safety check implies an external API | Local denylist behind `ISafetyProvider`; remote implementation stubbed, keeping runs offline and deterministic |

## 10. Definition of done

### Stage 1 (current scope)

1. Runs 1 and 2 complete, each producing a `RunSummary` generated from the event log.
2. Run 1's output passes `dotnet build`, `dotnet test`, and the independent conformance oracle.
3. Run 1's schema is created through the gated migration pipeline — the SQL is classified, reviewed by a human, and applied transactionally to `workload_test`, with a proven `Down()`.
4. The generated application does **not** migrate at startup; it verifies and fails fast.
5. Run 2 rejects Gate 1 at least once and records the clarification in the decision lineage.
6. Run 2 executes a demonstrably different graph shape from Run 1.
7. Both runs replay offline from cassettes with identical results.
8. Run 1's output is frozen and committed as `baseline/` for Stage 2.

### Stage 2 (deferred)

9. Roslyn impact analysis on Run 3 scores against `GROUND_TRUTH.md` at the agreed threshold.
10. Run 3 trips the migration change-control policy and requires human approval.
11. Run 3 passes the unchanged Run 1 conformance oracle — no regression across the lifecycle.
12. Run 4 executes the reduced graph, with no design stage and no Gate 2.
